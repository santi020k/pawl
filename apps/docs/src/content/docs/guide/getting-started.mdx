:::note[Before 1.0]
Pawl is on npm and tested against the real Biome and ESLint. Until 1.0, a minor release may change the API or the standard; the [changelog](/changelog/) says what each release changed.
:::

Pawl gives a repo one lint and format standard, run by the tools you choose, and a ratchet: the findings the repo already has are recorded once, and from then on only new ones fail.

## Requirements

Node 22.18 or later.

## Set up a repo

<Steps>

1. Run `init` at the root of the repo, with the package manager the repo uses.

   <Tabs syncKey="package-manager">
     <TabItem label="npm">

     ```sh
     npx @santi020k/pawl init
     ```

     </TabItem>
     <TabItem label="pnpm">

     ```sh
     pnpm dlx @santi020k/pawl init
     ```

     </TabItem>
     <TabItem label="yarn">

     ```sh
     yarn dlx @santi020k/pawl init
     ```

     </TabItem>
     <TabItem label="Bun">

     ```sh
     bunx @santi020k/pawl init
     ```

     </TabItem>
   </Tabs>

   `init` looks at the repo, shows what it will change, and asks before writing. In a terminal it asks how to set up the tools, then what else to add: the editor, coding agents, a pre-commit hook or a GitHub workflow. In CI or under a coding agent it asks nothing, uses `auto`, and adds what the options say.

2. Review the plan and accept it. `init` writes:

   - `biome.json`, a few lines that extend the standard;
   - `check` and `fix` scripts in `package.json`;
   - `.vscode/settings.json`, so the editor formats and fixes on save, `.vscode/extensions.json`, which recommends the editor extension, and `.vscode/tasks.json`, with tasks that put pawl's findings in the Problems panel (see [Editors](/guide/editors/));
   - `.pawl/baseline.json`, the findings the repo already has.

3. Commit the result, baseline included. From now on, `pawl check` fails only on new findings.

</Steps>

Pawl never deletes or overwrites a tool config you already have. It tells you what you can remove.

### Modes

| Mode             | What it does                                                        |
| ---------------- | ------------------------------------------------------------------- |
| `auto` (default) | Biome lints and formats. An existing ESLint setup is left in place. |
| `keep`           | Stay on the engine the repo uses today and add the ratchet on top.  |
| `biome`          | Biome only. Pawl stops running ESLint.                              |

Useful flags: `--yes`, `--dry-run`, `--mode <mode>`, `--workflow` (GitHub Actions: the check with annotations on the pull request, and the doctor report as an artifact), `--agents` (hooks that fix each edit for Claude Code, and for Cursor, Codex and Copilot where the repo uses them; a guard on the baseline for Claude Code and Codex; instructions in `AGENTS.md` that Claude Code and Gemini CLI read too; a pawl skill), `--hooks` (a pre-commit hook), `--no-editor`, `--no-install`. The [CLI reference](/reference/cli/) lists them all.

Already on ESLint? [`pawl migrate`](/guide/migrate/) turns your config into a pawl policy first.

## Daily use

```sh
pawl check              # lint, check formatting, apply the ratchet
pawl check --changed    # only files changed against HEAD
pawl fix                # apply safe fixes and format
pawl baseline           # accept the current findings as the new baseline
pawl sync               # rewrite biome.json after the policy changed
pawl upgrade            # install the tool versions this pawl works with, then sync
pawl explain no-console # what a rule does, and its level in this repo
pawl doctor             # check the setup and the tool versions
```

The engines also work on their own: `npx biome check` and `npx eslint .` use the same config files.

## Exit codes

| Code | Meaning                                                                                       |
| ---- | --------------------------------------------------------------------------------------------- |
| 0    | No new errors                                                                                 |
| 1    | New errors, or more new warnings than the limit allows                                        |
| 2    | A setup problem: an engine could not run, or, with `--ci`, the config drifted from the policy |

`--ci` is on automatically when the `CI` environment variable is set, as CI services set it; an empty value, `0` and `false` mean it is not.
