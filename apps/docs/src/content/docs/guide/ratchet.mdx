A pawl is the part of a ratchet that stops it slipping backward. Pawl does the same for a codebase: the findings a repo has when it adopts the standard are recorded once, and from then on quality can only move forward.

<RatchetChart />

## Adopt a baseline in an existing repo

Start at the repository root. If you are moving an existing ESLint configuration, read the [migration guide](/guide/migrate/) first.

### Record existing findings

```sh
npx @santi020k/pawl init
npx pawl check
```

Review the setup plan and accept it when it matches your project. Once the tools are installed and the check can run, `init` records the existing findings in `.pawl/baseline.json`. The next check allows those counts, so you can adopt the standard before fixing every old finding. Review and commit the generated configuration, dependency changes and baseline together.

### Check a new finding

For example, suppose the baseline allows one `eqeqeq` finding in `src/server.ts`, as in the JSON below. Adding a second comparison that violates that rule in the same file exceeds the count. Run:

```sh
npx pawl check
```

The check fails because the count increased and reports both comparisons. Fix the new comparison and check again; the original finding is still allowed. Do not run `pawl baseline` to clear this failure unless you intend to accept the additional finding.

### Lower the baseline after a fix

Fix the original comparison too, then run:

```sh
npx pawl check
npx pawl baseline
npx pawl check
```

Review the baseline diff and commit it with the code fix. With the count lowered, reintroducing that finding fails the next check. Use `pawl check --ci` in [CI](/guide/ci/) to enforce the committed baseline for the team.

## The baseline

`.pawl/baseline.json` records how many findings of each rule each file had when the repo adopted the standard, and how many assertions and skipped tests each test file had. `pawl init` writes it. Commit it.

```json title=".pawl/baseline.json"
{
  "version": 1,
  "findings": {
    "src/legacy.ts": {
      "@typescript-eslint/no-explicit-any": 1,
      "@typescript-eslint/prefer-for-of": 1,
      "biome:correctness/noInnerDeclarations": 1,
      "no-var": 2
    },
    "src/server.ts": {
      "eqeqeq": 1
    }
  },
  "suppressions": {},
  "tests": {
    "src/server.test.ts": { "assertions": 14, "skipped": 0 }
  }
}
```

## What fails

- Findings within those counts are allowed.
- Anything beyond them fails the check.
- A file that gains a disable comment (`biome-ignore`, `eslint-disable`, `oxlint-disable`, `@ts-ignore`, `@ts-expect-error`, `@ts-nocheck`) fails with `pawl/no-new-disable`. Pawl looks for them in scripts and components, and in the stylesheets, JSON, GraphQL, YAML and TOML files a linter reads.

- A test file that loses assertions or gains a skipped test fails with `pawl/no-weaker-tests`. See [Tests that get weaker](#tests-that-get-weaker).

The last two matter most when an agent writes the code: switching a check off, or weakening the test that caught the problem, is not a way past it.

## Tests that get weaker

An agent can turn a failing test green without fixing anything: delete the assertion, swap `toEqual({ id: 7, status: 'settled' })` for `toBeTruthy()`, or skip the test. So the baseline counts, for each test file, two things:

- **Assertions that pin a value**: `expect(...)`, `expect.soft` and `expect.poll`, `expectTypeOf`, `assertType`, and `node:assert`. A check that passes for almost any value takes one away from the count: `toBeTruthy()`, `toBeFalsy()`, `toBeDefined()`, `.not.toBeNull()`, `.not.toBeUndefined()`, `expect.anything()`, `expect.any()`, and a bare `assert()` or `assert.ok()`. So weakening an assertion lowers the count, and adding a new weak one leaves it as it was.
- **Skipped tests**: `.skip`, `.todo` and Playwright's `.fixme` on `describe`, `it`, `test` and the like, and `xit`, `xdescribe` and `xtest`. A conditional skip such as `it.skipIf` is not counted.

A test file is a `.test`, `.spec`, `.cy` or `.e2e` script, or any script under a `__tests__` folder.

A file with fewer assertions than the baseline recorded fails, and so does each new skipped test in a file with more skips than it recorded. A test file the baseline has no count for, such as a new one, has no floor until the next `pawl baseline`. On a check of the whole repo, a counted test file that is gone fails too, unless new test files have at least as many assertions, as when the file was renamed or split; a check of some files cannot tell.

Tests that got stronger count as an improvement, like fewer findings: `pawl check` says so, and `pawl baseline` raises the floor.

Turn the rule down for some files with an override, as for any rule:

```ts
export default definePolicy({
  overrides: [{ files: ['e2e/**'], rules: { 'pawl/no-weaker-tests': 'warn' } }]
})
```

The counts come from a line scan, so an assertion inside a string, such as a code sample in a test of a linter, counts as one too. That keeps the counts stable; it only matters when such a string changes.

A baseline written by a version of pawl before 0.5 has no test counts, so tests have no floor yet. `pawl check` says so when it finds nothing else to report; run `pawl baseline` then to start counting.

## Locking in improvements

When the code improves, `pawl check` says so:

```txt
No new findings.
2 existing findings allowed by the baseline.
The code has fewer findings, or stronger tests, than the baseline records. Run "pawl baseline" to lock that in.
```

Run `pawl baseline` to record the lower counts, and commit the file. From then on the repo cannot slip back past the improvement.

`pawl baseline` records whatever the code has at that moment. A team can also use it to accept findings on purpose, and that shows up in review as a change to `.pawl/baseline.json`.

It writes the file only when the whole check ran. When an engine is missing or fails, the baseline is left as it was: a baseline recorded from half the findings would fail the other half later as new.

## A baseline that allows more

Recording findings makes the check allow more, and nothing else in the check would notice: the new findings are old ones now. So a check with `--since <ref>` also compares `.pawl/baseline.json` with the one where the branch left `<ref>`, and fails at the baseline file when it allows more: more findings or disable comments in a file, fewer assertions or more skipped tests in a test file, or a test file it no longer counts.

```txt
.pawl/baseline.json:1:1  error  The baseline allows more than it does on origin/main: src/a.ts: 2 more no-console findings. Fix the findings instead of recording them. If a person decided to accept them, add "Pawl-Baseline: accept" to a commit message on this branch.  pawl/no-baseline-growth
```

When accepting the findings is what you want, as after an upgrade that adds a rule, say so in a commit on the branch:

```txt
chore: accept the findings of the new rules

Pawl-Baseline: accept
```

Any commit between `<ref>` and `HEAD` with that trailer accepts the baseline as the branch leaves it. The trailer is in the history for whoever reviews the pull request. On GitHub, a `CODEOWNERS` entry for `.pawl/` adds a review by the people who own the standard as well. A branch that adopts pawl and records its first baseline needs the trailer too.

Set `pawl/no-baseline-growth` to `off` in the policy to turn this off. Without `--since` there is no base to compare with, so a check of the whole repo does not run it; see [Only what a pull request changed](/guide/ci/#only-what-a-pull-request-changed) for a pull request job that does.

## When two branches change it

The file is plain JSON with sorted keys, so most merges are clean. When git cannot merge it, resolve the conflict by hand or run `pawl baseline` on the merged code. Until then `pawl check` stops with exit code 2, because without the baseline every old finding would count as new:

```txt
setup  .pawl/baseline.json cannot be read: it is not valid JSON, or not a baseline this version of pawl knows.
       Resolve the merge conflict in it, or run "pawl baseline" to record the findings again.
```

## Why per file and rule

Counts are per file and rule, not per line, so moving code around does not break the baseline, and neither do edits or merges.

The cost is that when a file goes over its count, every finding of that rule in the file is shown, because pawl cannot tell which one is new.
