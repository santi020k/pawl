# @santi020k/pawl

## 0.6.0

### Minor Changes

- Findings show where people read them in CI: on their line in the pull request, and in code scanning.

  - `--format github` prints a GitHub Actions annotation for each new finding, with its file, line, column, rule and fix, so it shows on that line in the pull request. Setup problems and the warning limit show on the run; in CI every setup problem is an error. The annotations sit in a log group that GitHub folds away, and the plain report follows, so the log reads as before.
  - In a GitHub Actions job, `pawl check` and `pawl fix` now use `--format github` when no format is given, so a workflow written by an earlier version also puts each new finding on its line in the pull request. A coding agent that runs pawl there still gets `agent`, and `--format` and `PAWL_FORMAT` still win. If a step reads what pawl prints, name the format it reads, or set `PAWL_FORMAT=pretty` on the step for the plain report alone.
  - `--format sarif` prints the new findings as SARIF 2.1.0, the format GitHub code scanning and other code-scanning tools read. Each finding is a result with its rule, level and location, and each rule from pawl's catalog carries its summary and its fix. Setup problems are notifications of the run, and `executionSuccessful` is false when the check could not complete. Upload the file with `github/codeql-action/upload-sarif`; the [CI guide](https://pawl.santi020k.com/guide/ci/#code-scanning-with-sarif) has the steps and the permissions.
  - Findings the baseline allows are left out of both formats.
  - Under GitHub Actions, both formats name files from the root of the repository the job checked out, also when pawl runs in a folder below it. SARIF percent-encodes the characters a URI cannot hold, such as spaces, `#` and `?`, and the plain report after the annotations cannot start a workflow command, whatever a finding's message says.
  - The workflow `init --workflow` writes runs `pawl check --ci --format github`.
  - The API gains `formatGithub`, `formatSarif` and the `CiOutputOptions` type. `OutputFormat` takes `github` and `sarif`, and `format` takes the `ci` and `base` options. Nothing is removed, but code that handles every `OutputFormat` by name needs a case for the two new ones.

- `pawl upgrade` installs the tool versions this pawl works with, then syncs the config files. Run it after you move to a new version of pawl.

  It installs each tool that is installed and outside the versions pawl works with, as `pawl doctor` reports them. Biome, Oxlint and `oxlint-tsgolint` go to the exact version pawl is built for. ESLint, Prettier, `typescript-eslint` and the plugins of the packs the policy names go to the newest version of the major version they are on, such as `eslint@9` for ESLint 9.30, when it has one pawl works with; only a tool whose major version has none moves to a new one, the nearest pawl works with, and the plan says so. It uses the project's own package manager, and runs `pawl sync` once the new versions are in place. `--dry-run` shows what it would install and changes nothing, and `--no-install` only syncs. A tool that is not installed is left to `pawl add` and `pawl init`, and Node to you.

  - In a workspace, a tool goes into each package that declares it, in the dependency group it is in there, and into the root only when no package declares it. A package with no name, which no install command can point at, gets a note with what to install there.
  - Moving `eslint-plugin-vue` from 9 to 10 also installs `vue-eslint-parser` 10, which the plugin takes as a peer from version 10 on. Under npm it goes first, in a command of its own, because npm cannot swap the plugin and the parser its old version brought in one install and stops with `ERESOLVE`.

- A guard on the baseline, so neither a coding agent nor a branch can make the check allow more without a person deciding it.

  - `init --agents` adds a hook that runs before each tool, `PreToolUse`, for Claude Code and Codex. When the agent is about to edit `.pawl/baseline.json`, the policy or an engine config, run `pawl baseline`, or run a command that writes the baseline, Claude Code asks you first and shows what the call would change. Codex cannot ask yet, so the hook refuses a change to the baseline, says why, and lets an edit to the policy or an engine config through. Run `pawl init --agents` again to add the hook next to the ones pawl already wrote.
  - The hook runs `npx --no pawl check --hook`, the stop hook's command: pawl reads which event it is from the hook's input. It loads no project and runs no engine, so a tool call that changes none of those files goes through at once.
  - Copilot and Cursor get no guard. Copilot refuses a tool when a hook before it fails, as `npx --no pawl` does in a clone before the install, so the guard would stop every tool there. Cursor has no hook before an edit that can ask. `pawl check --hook` still reads Copilot's own `preToolUse` input, for a hook you set up by hand.
  - `pawl check --since <ref>` also fails with `pawl/no-baseline-growth` when `.pawl/baseline.json` allows more than it does where the branch left `<ref>`: more findings or disable comments in a file, fewer assertions, more skipped tests or more retries, raised timeouts and fixed sleeps in a test file, or a test file it no longer counts. A branch that records its first baseline counts too. To accept it, a person adds a `Pawl-Baseline: accept` trailer to any commit on the branch. Set the rule to `off` in the policy to turn it off.

- The test ratchet also counts what can make a flaky test pass now and then instead of fixing it, so a test cannot be kept green with a retry or a longer wait:

  - a retry: `retry: 2`, `retries: 2`, `test.retry(2)`, `jest.retryTimes(2)`, `this.retries(2)`;
  - a raised timeout: a `timeout` option, `jest.setTimeout`, `test.setTimeout`, `test.slow()`, or a number after the test's function;
  - a fixed sleep: `waitForTimeout`, `cy.wait(500)`, `setTimeout(resolve, 500)`, `sleep(500)`.

  A test file with more of those lines than the baseline recorded fails as `pawl/no-weaker-tests`. A `timeout` on an assertion that retries, such as `expect(...).toBeVisible({ timeout })` or `waitFor(..., { timeout })`, is how to wait well and does not count. A baseline from an earlier version has no count for these yet: once `pawl check` passes, run `pawl baseline` and commit `.pawl/baseline.json` to start counting. In the API, `TestCounts` has an optional `masks`.

### Patch Changes

- Where Biome or Oxlint is the linter and the policy names the `javascript` or `typescript` pack, as `pawl migrate` writes it, ESLint leaves off the rules the linter already enforces. It ran them at the level the plugin's preset gave them, so `pawl check` reported a `debugger` or an unused variable twice, and a rule the policy turned off, such as `@typescript-eslint/no-non-null-assertion` after a migration, still failed under ESLint.

- Where Biome is the linter, a duplicate key in a `.json` or `.jsonc` file is reported once, by Biome. The JSON pack reported it again as `jsonc/no-dupe-keys`; it still checks `.json5` files, which Biome does not read. The same goes for the rules of a plugin's own preset that Biome or Oxlint enforces, which the Vue, Svelte, Astro and format packs left on: a one-word Vue component name was reported by both Biome and `vue/multi-word-component-names`. A rule the standard holds back in the fast linter as unstable keeps the level the plugin's preset gives it.

- A project that moves its linting or formatting back to Biome, from Oxlint, ESLint or Prettier, is checked again. Pawl had written `"enabled": false` for Biome's linter or formatter into biome.json, and kept it after the policy changed back, while `pawl doctor` said biome.json was in line with the policy: Biome then linted or formatted nothing, and the check passed. A biome.json that switches off what the policy has Biome do is now out of date, `biome-config-stale`, and `pawl sync` switches it on again.

- `pawl check`, `pawl fix` and `pawl baseline` work from a package folder of a monorepo, or from any folder below the root such as `src`. Pawl looked for its config in the folder it started in, so in a package it said "No biome.json found. Run pawl init" while the root had one, and `pawl baseline` would have written a second baseline there. It now runs from the nearest folder above, in the same git repository, that has pawl's policy, its baseline or an engine config, as at the root, and takes the files you name from the folder you are in: `pawl check .` checks that package only. The hooks of coding agents started in a package do the same.

- With ESLint as the linter, the standard's rules for scripts reach the scripts of `.vue`, `.svelte` and `.astro` files, through the parser the Vue, Svelte and Astro packs set up. A `debugger`, a `var` or an `==` in a `<script setup>` or an Astro frontmatter passed the check before. In a TypeScript project typescript-eslint's rules run there as in a `.ts` file, except the ones that need type information, since a component has no TypeScript program; policy overrides and locked rules reach those scripts the same way. Where Biome is the linter, the rules it enforces stay Biome's there too.

- `pawl sync --dry-run` with nothing to sync says "Config files are up to date." instead of printing two blank lines before "Dry run. Nothing was changed.". The dry runs of `sync`, `add` and `upgrade` no longer start with a blank line when they have nothing to list, nor print two in a row when there are no notes.

- The oldest versions pawl declares for ESLint, `typescript-eslint` and the pack plugins are now ones that work with it. Each was found by running every pack against its plugin at that version, with ESLint at its own floor. `pawl doctor` reports an installed version below its floor as a problem, which also fails the doctor step of the workflow `init --workflow` writes. Run `pawl upgrade` to move it.

  - ESLint is now `>=9.35.0`, up from `>=9.22.0`: the standard uses `no-unassigned-vars` and `preserve-caught-error`, which ESLint added in 9.27 and 9.35, so an older ESLint stopped because it could not find them.
  - `typescript-eslint` is now `>=8.15.0`, up from `>=8.0.0`: older versions crash in `no-unused-expressions` under ESLint 9.35.
  - Plugins that lacked rules the packs set, or did not load, have a higher floor: `@eslint-react/eslint-plugin` 4.2.1, `@darraghor/eslint-plugin-nestjs-typed` 7.4.0, `eslint-plugin-astro` 1.0.3 and `eslint-plugin-i18next` 6.1.0.
  - The nine plugins that took any version now have a floor: `eslint-plugin-solid` 0.14.1, `eslint-plugin-lit` 1.12.0, `@tanstack/eslint-plugin-query` 5.43.1, `eslint-plugin-compat` 6.0.0, `eslint-plugin-depend` 1.0.0, `eslint-plugin-toml` 0.10.0, `@html-eslint/eslint-plugin` 0.41.0, `eslint-plugin-hono` 1.0.0 and `@tanstack/eslint-plugin-router` 1.58.0.

- Two `pawl check --eslint-cache` runs that start at the same time in a project without an ESLint cache yet both run. The second one found the cache directory the first had just taken and stopped with "ESLint cache inputs or storage could not be read safely", a setup problem with exit code 2. It now checks that the directory is pawl's, as it does for any cache that exists, and goes on.

- `pawl init --engine eslint` installs every plugin the standard needs when ESLint is the linter, so `pawl doctor` finds none missing after it. It installed ESLint, `@eslint/js` and `typescript-eslint` only, and the doctor then exited with code 2 for the rules Biome would have run: those of `eslint-plugin-unicorn`, `eslint-plugin-promise`, `eslint-plugin-unused-imports`, `eslint-plugin-import`, `eslint-plugin-no-only-tests` and `@vitest/eslint-plugin`. `init`, and `pawl add` in a project that ESLint lints, now install each plugin the doctor would ask for, and with `--no-install` write them into `devDependencies`, a pack's plugin from its floor. Under npm they go in last, in a command of their own, so that a plugin whose peer range npm refuses, as `eslint-plugin-import`'s leaves out ESLint 10, does not stop pawl and ESLint from installing.

- A syntax error in a YAML or GraphQL file, or in some Vue files, no longer stops the ESLint part of the check with "Could not read ESLint's report". Those parsers count columns from 0, and pawl refused a report with a column of 0, so the check dropped every ESLint finding of the run and reported a setup problem instead. The syntax error is now a finding on its line, `eslint:parse`, beside the others.

- Installing a pinned tool keeps it pinned, and installing into a Yarn 1 workspace works.

  - Under npm, the exact versions pawl installs, Biome's in `pawl init`, and Biome's and Oxlint's in `pawl upgrade`, go in with `--save-exact`, in a command of their own before the rest. npm wrote `^` before the version it was given, so package.json allowed a newer Biome than the one pawl reads, and the next fresh install could bring one. pnpm, Yarn and Bun already keep an exact version exact.
  - At the root of a Yarn 1 workspace, `pawl upgrade`, `pawl init` and `pawl add` now pass `-W`, without which Yarn 1 refuses to add to the root, so the install failed. Yarn 2 and later, which refuse `-W`, still get none; pawl tells them apart by the `packageManager` field, `.yarnrc.yml` and the lockfile.

- The test ratchet counts a `retry`, `retries` or `timeout` option only where it raises them for a test: on `test`, `it`, `describe`, their hooks, `test.describe.configure` or `vi.setConfig`. A timeout on an assertion that retries or on `waitFor` no longer counts when the formatter puts it on a line of its own, nor does an option of the code a test calls, such as `createClient({ timeout: 100 })`, or one written in a string, a template or a comment. A fixed sleep on the same line as a retrying assertion now counts.

- The packs whose plugin ships its preset as a flat config of several blocks work again: Vue, Svelte, YAML, JSONC, TOML, Storybook and Astro 3. In 0.5.0, every check with one of them stopped with "Pawl cannot enforce requested ESLint rules".

  - Pawl looked for a rule's plugin only in the block that set the rule, and these presets register the plugin in an earlier block. It now looks in every block, as ESLint does.
  - A block of a pack's preset that names no files keeps to the pack's own files when it sets a parser, a language or a processor, so the HTML pack no longer parses scripts as HTML. A block with rules only keeps to the scripts and the pack's own files, so Vue's rules no longer reach the Markdown, JSON or YAML that another pack parses, where they crashed ESLint.
  - A pack registers the plugin object its preset registers, so a plugin whose ES module build exports another object than its presets use, such as `eslint-plugin-astro` 1.x, no longer stops ESLint with "Cannot redefine plugin".

- `pawl/no-baseline-growth` fails a branch whose baseline no longer counts the tests at all, or no longer counts the retries, raised timeouts and fixed sleeps of a test file. Both take a floor away, as a test file that is no longer counted does, and passed `check --since` without a word.

- The guard before each tool reads a shell command for what it runs and what it writes, instead of looking for words in its text. Codex no longer refuses a command that only reads the baseline, such as `cat .pawl/baseline.json 2>&1`, `jq … .pawl/baseline.json > out.json` or `cp .pawl/baseline.json /tmp/`, or one that only mentions pawl and its baseline in a string, such as a commit message or a search. It now catches what got past it: `sed --in-place` and `perl -pi`, `pawl baseline` inside `bash -c` or `$(…)`, a command split over lines, a Node or Python script that writes the baseline, an `apply_patch` run from the shell, a command that removes or restores the `.pawl` folder, and PowerShell's `Set-Content`, `Out-File`, `Copy-Item` and `Remove-Item` with Windows paths. Claude Code also asks before a command writes the policy or an engine config, as it does before an edit of one.

  The guard now covers the whole repository when the agent works in a package of a monorepo: an edit of the baseline or the policy at the top of the repository asked nobody when the hook started in the package's folder. `init --agents` also adds `PowerShell` to the tools the guard runs before in Claude Code, which on Windows runs its shell commands there, and without Git Bash only there.

- A check that did not run right can no longer pass as a clean one, and pawl reads the disk more carefully.

  - When Biome or Oxlint exits with a code above 1, prints a report entry pawl cannot read, or exits with a code its own report contradicts, the check stops with a setup problem and exit code 2. A Biome or Oxlint config that the engine cannot load is one such case.
  - A `.pawl/baseline.json` with a count that is not a whole number of zero or more cannot be read, like one with a merge conflict: the check stops with exit code 2 and says to run `pawl baseline`.
  - Pawl's own checks skip a folder that git lists as a file, such as a submodule. Symbolic links to files are still checked.
  - A project root given with a trailing slash, or through a symbolic link, names files the same way as any other root.
  - A JSON file pawl edits keeps a key such as `__proto__` or `constructor` as a plain key.
  - `--eslint-cache` reads the files it fingerprints in chunks, and refuses a cache folder or ownership file that is a broken symbolic link.
  - A check of the whole project lists the project's files once, not once for each of pawl's own checks.

- `check --help` says that `--hook` is also the stop hook and the guard before each tool, and that `pretty` is the default except for a coding agent, which gets `agent`, and in GitHub Actions, which gets `github`. `init --workflow` says the workflow runs `pawl check --ci --format github`, as the file it writes does. The skill `init --agents` writes, and the plugin's, say that Claude Code asks before `pawl baseline` and Codex refuses it, and that retries, raised timeouts and fixed sleeps in a test fail the check too.

- With ESLint as the linter, the standard's `import/*` rules run with `eslint-plugin-import-x` in a project that does not have `eslint-plugin-import`, and `init` and `add` install it. `eslint-plugin-import` leaves ESLint 10 out of its peer range, so under npm `pawl init --engine eslint` failed at its plugin install with ERESOLVE. A project that already has `eslint-plugin-import` keeps using it. Pawl checks that the plugin in use implements each rule it runs: a rule it lacks is listed by `pawl doctor` instead of stopping ESLint with "Could not find rule".

- Running `pawl init` again, as `pawl init --hooks` to add the pre-commit hook, keeps the linter and formatter the policy names. It chose Biome whenever no `--engine` was given, so in a project set up for Oxlint it printed "Lint: Biome", planned to rewrite biome.json for Biome as the linter, and told you to choose Oxlint. It now starts from the policy's `engine` and `formatter`, and an option still wins over them.

- The JSON pack no longer sorts keys. With `jsonc/sort-keys` on, `pawl fix` rewrote the keys of `package.json`, `tsconfig.json` and the `.vscode/tasks.json` pawl writes in alphabetical order, away from the order people and tools read them in. Turn the rule on in an override for the files where the order means nothing, such as `{ files: ['src/locales/**/*.json'], rules: { 'jsonc/sort-keys': 'warn' } }`.

- An engine older than this pawl works with is one setup problem, with exit code 2, instead of pages of the engine's own errors. With Biome 2.5.0, `pawl check` printed about 50 KB of Biome config errors, twice that with `--format github`, and with ESLint 9.30 it said "Could not find preserve-caught-error". Pawl now reads the version of Biome, Oxlint, ESLint and Prettier before it runs them, and one that is older than the versions it declares does not run: the problem names the installed version and the versions pawl works with, and says to run `pawl upgrade`. A version newer than the one pawl pins for Biome still runs, and `pawl doctor` still reports it.

- `pawl check` stops with a setup problem, exit code 2, when the plugin of a pack is installed but fails to load, for example because a peer it needs is missing. A pack the project's dependencies switch on was left out of the check without a word, so the check passed without its rules and only `pawl doctor` said why. A plugin that is not installed at all still only suggests its pack.

- The baseline never accepts a parse error. `pawl init` and `pawl baseline` recorded `eslint:parse`, `biome:parse` and the other engines' parse errors like any finding, so a file with a syntax error passed every check after that, and the engine never checked it again. Now they record the other findings, name each file that did not parse with its first error, and leave the parse errors to fail the check until the file parses; `pawl baseline` then exits with 1. A parse error that a baseline from an earlier pawl counts fails too. In the API, `createBaseline` leaves parse errors out, `applyBaseline` never allows one, and `check` with `updateBaseline` returns them in `findings`.

- The pre-commit hook `init --hooks` writes no longer fails a commit for a file that is not in it. `pawl check --changed` looks at the files changed against HEAD and the untracked ones, so an untracked file with a finding, even one only to format, stopped every commit until it was deleted or fixed. While git runs the hooks of a commit, `--changed` now takes the files the commit changes, from the index git commits; a change that is not staged is left out too. Hooks written by an earlier version get this without a change.

- In `--format sarif`, pawl's own line scans describe their rules as the catalog's rules are described: `pawl/no-hidden-characters`, the Docker and Compose checks and the Markdown checks now have their summary, how to fix what they find, and a link to their part of the docs, where they had only their name.

- The skill `init --agents` writes also tells agents not to widen the ignores in the policy or an engine config, and what the guard and `--since` do when an agent records findings in the baseline. Run `pawl init --agents` again to update a skill pawl wrote. The agent plugin's skill now comes from the same text, so it covers hidden characters and weaker tests too; the plugin is at version 0.1.1.

- The Svelte pack reads `.svelte.ts` modules in a TypeScript project. eslint-plugin-svelte hands those files to its own parser, which read their script as JavaScript, so every module with a type in it failed the check with "Parsing error: Unexpected token :". It now gets typescript-eslint's parser, as the `<script lang="ts">` of a component does, and keeps the rules that need type information.

- With ESLint as the linter in a TypeScript project, `pawl.config.ts` parses when the `tsconfig.json` leaves it out, as the Vite and Svelte templates do. typescript-eslint's project service could not find it, so the check reported `eslint:parse` on the file `init` had just written, and `init` recorded it in the baseline. The config files of pawl, ESLint and Oxlint written in TypeScript now get the standard's rules without type information, whether or not a tsconfig includes them.

- The Vue and Svelte packs read `<script lang="ts">` in a TypeScript project: they hand each component's script to typescript-eslint's parser. Their presets leave it to espree, so every component with a type in it failed the check with "Parsing error: Unexpected token".

- `pawl init` and `pawl add` install `typescript-eslint` in a TypeScript project also when ESLint runs next to Biome: for a Vue, Svelte or Astro project, which Biome does not fully lint, or for a pack. ESLint lints the scripts too, so without it every TypeScript file with a type in it failed with "Parsing error: Unexpected token": `init` recorded those in the baseline, a new typed file failed the check, and `pawl doctor` asked for `typescript-eslint` that nothing had installed.

- An `eslint-disable` or `eslint-enable` comment that switches off nothing is reported as `eslint:unused-disable-directive`. It was reported as `eslint:parse`, as if ESLint could not read the file, and `pawl explain` said to fix a syntax error. `pawl fix` removes the comment. A baseline that recorded one as `eslint:parse` no longer covers it: run `pawl fix`.

- With ESLint as the linter, the standard's `vitest/*` rules apply only in a project that tests with Vitest: one that depends on `vitest`, or whose policy declares it in `testRunners`. In a project that tests with Jest or `node:test`, they asked for `@vitest/eslint-plugin`, which `init` and `add` then installed, and under npm that install failed in a TypeScript 5 project, outside the plugin's peer range. A policy that names a `vitest/*` rule still gets it.

- The fix of a `pawl/no-weaker-tests` finding matches what the test file lost or gained. Every finding of the rule said "Put back the assertions with the values they pinned, or make the skipped test pass", also for a new retry, a raised timeout or a fixed sleep. A finding now names which of the three it found, and its fix, in `--format agent`, `github` and `sarif` and in the terminal, is the one for that: fix why the test fails now and then for a retry, wait for what the test waits for for a raised timeout, and wait with an assertion that retries for a fixed sleep. The rule's summary also names retries, raised timeouts and fixed sleeps.

- `pawl add` and `pawl init` with `--no-install` write a version range for the Solid, TOML and HTML plugins that a package manager can install. They wrote `^0.0.0`, from the major version of the plugin's floor, which no version of those plugins satisfies, so the next install failed. The range of a pack's plugin now starts at its floor, such as `^0.14.1` for `eslint-plugin-solid` and `^4.2.1` for `@eslint-react/eslint-plugin`, and `typescript-eslint` is written as `^8.15.0`, the floor pawl declares, instead of `^8.0.0`.

## 0.5.0

### Minor Changes

- Report known Astro virtual-import and scoped parser limitations in `pawl doctor`, including the separate Astro validators to retain. JSON doctor reports expose advisory `limitations` separately from setup problems. No rules are suppressed and existing configuration is preserved.

- Detect competing Biome and ESLint import-sort owners before applying fixes. The check resolves ESLint rules for the selected files, reports unknown custom ownership explicitly, and preserves semantic import checks.

- Migrate scoped ESLint rules onto policies that already contain file overrides. Explicit source scopes replay after parent scopes, while locked rule floors remain enforced. Parent exceptions remain where the source does not override them; unsafe inherited option combinations still stop before any writes.

- Add opt-in `pawl check --eslint-cache` and `check({ eslintCache: true })` with an explicit deterministic-input declaration. Whole-project, dependency, runtime and environment fingerprints guard native ESLint content caching; corrupt cache state reruns cold and failed or interrupted checks cannot publish reusable state. Fixes remain uncached. Also report signal-terminated engine processes as setup failures even if they printed a partial report.

- Add explicit `testRunners` file scopes for mixed Vitest, Jest, Playwright and Node test projects. Runner-specific assertion conventions stay in their declared scopes while shared focused/skipped-test checks retain their floors. Reject empty, unknown or exclusion-based scopes and attempts to narrow locked runner rules. Document the pinned engines' conditional Playwright and Node skip coverage boundaries.

- Compose existing framework ESLint configs through the public helpers, preserve host parsers, enforce locked rule floors after local exceptions, and route processor fragments without TypeScript project services. Add explicit pack file ownership and consume policy test-runner scopes. Correct literal-bracket workspace ownership and ordered exclusion/re-inclusion patterns at the ESLint boundary.

  Reject broad custom processor-output scopes and physical directory collisions so `untypedFiles` cannot silently disable locked type-aware rules on physical source. Verify each configuration snapshot with a bounded directory scan that fails closed on ambiguous links, cycles and exhausted limits.

- Add advisory root/workspace lint traversal diagnostics to doctor, with explicit unknown scopes and a documented recipe for removing duplicate work without losing engine coverage.

- Expose shared plugin resolution roots and explicit plugin namespace bindings through all ESLint helpers. Validate requested plugin rule implementations and reject missing requested rules or packs as setup failures instead of silently omitting them. Keep ordinary default coverage limitations in the planner report.

  Resolve import-only public package roots and concrete subpath exports in declaration order, including package self references. Denied exports no longer fall back to package main or private entries; unsupported pattern exports produce an actionable error.

- Add `pawl init --no-baseline` and the `planInit({ baseline: false })` option for adoption without accepting existing findings. Dry runs describe baseline handling, shared policy locks remain enforced, and existing baseline files are preserved.

- Add conservative task reachability diagnostics for literal package scripts and Turbo cache settings. Report cached, uncached, shared and unknown consumers without automatically exempting files from lint checks.

- Track generated Biome override ownership with versioned content fingerprints. Sync updates unchanged generated scopes, including removing obsolete scopes, while preserving unknown or edited arrays. Plans list recoverable backups and ownership writes; stale plans, symbolic links, unknown metadata files and conflicting backups are refused before configuration writes. Older configurations require explicit reviewed reconciliation rather than inferred ownership.

- Version JSON check reports with an additive `reportVersion: 1` field and export `readCheckReport` for consumers that validate captured output against the actual process exit code. ## 0.1.0

### Minor Changes

- First public release of pawl: one standard for Biome, Oxlint, ESLint and Prettier, with guards for AI SDKs, Docker and Markdown checks, optional packs, a ratchet baseline and agent-friendly output.
- Covers the rules of `@santi020k/eslint-config-basic` without a plugin wherever Biome or Oxlint has one, with guards for Zod, Testing Library and Nuxt, and Markdown checks of pawl's own.
- The standard has 200 rules, including the `jsx-a11y` and `promise` rules that Biome or Oxlint enforce without the plugin. The Stencil pack uses the official `@stencil/eslint-plugin`.
- The policy takes path-scoped `overrides`, a `runtime`, `detect`, `gitignore`, `defaultIgnores` and `maxWarnings`, and refuses unknown keys. A JSON schema ships as `@santi020k/pawl/schema.json`.
- Every engine and pawl's own checks share one ignore list and follow `.gitignore`.
- `pawl doctor --format json` reports the setup and checks Node, Biome and plugin versions; `pawl check --max-warnings <n>` fails on too many warnings.
